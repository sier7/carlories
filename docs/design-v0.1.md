# 个人卡路里与营养记录应用 · 设计草案 v0.1

> 状态：讨论稿，未开始编码。
> 本文档中标记 ⚠️ 的是**尚未决策**的分歧点，需要确认后才进入实现。

---

## 1. 定位与原则

**定位**：一个人用的「摄入计算器 + 个人食物数据库」。不是估算器，不是社交产品，不做推荐算法。

四条原则，后面所有设计决定都从这四条推导：

1. **乘法，而非猜测。** 日常记录必须退化成 `份量 × 库中已核对的值`。估算的责任前移到建库阶段，一次性做对，而不是每天重估一遍。
2. **可审计。** 任何显示的数字都能一路展开到原始乘法，中间没有修正系数、没有黑箱。
3. **诚实。** 没记就报没记。缺记录的当天，数字偏低，应用必须主动说明，而不是假装它是个完整答案。
4. **数据属于你。** 纯本地存储，一键导出，随时可迁走。

## 2. 架构

```
iPhone 主屏幕
└── PWA（静态网页应用，离线可用）
    ├── ui/       界面
    ├── core/     纯逻辑：食物库、份量换算、营养计算、日汇总、目标判定
    │             （无 DOM、无存储依赖，可单独测试）
    ├── storage/  IndexedDB 适配层
    └── health/   健康数据导入适配层
```

- **托管**：GitHub Pages。只托管**代码**，饮食记录始终留在手机本地。
- **数据**：IndexedDB，仅本机。无账号、无同步、无后端。
- **健康数据桥**：iOS 快捷指令 → 剪贴板 → 应用内一键导入（见 §7）。

**为什么这样分层**：`core/` 不依赖任何浏览器 API。将来若换成原生 SwiftUI 外壳，只需替换 `ui/` 和 `health/`，全部业务逻辑可复用。

## 3. 数据模型

### 3.1 Food（食材条目）—— 最小可复用单位

| 字段 | 说明 |
|---|---|
| `name` | 如「鸡蛋（全蛋）」 |
| `basis` | 基准量，二选一：`per100g` 或 `perServing{ servingGrams, servingLabel }` |
| `energy_kcal` | 每基准量的热量 |
| `protein_g` / `fat_g` / `carb_g` | 三大营养素，每基准量 |
| `fiber_g` / `sodium_mg` | 可选 |
| `state` | `raw`（生）/ `cooked`（熟）/ `n/a`。**必填**，见 §4.2 |
| `source` | 数据来源备注，如「包装标签」「自测」「参考值待核对」 |
| `verified` | 是否已人工核对。未核对的条目在界面上有明确标记 |

### 3.2 Dish（组合 / 常吃的一餐）—— ❌ 已取消

原本设计了两层模型：食材 + 组合，用组合把「常吃的一餐」一键记录。

**v0.2 决定取消。** 理由是用户的实际饮食每天都不同，组合用不上；
而「快速记录」这个真实需求，由 §3.6 的历史索引更好地解决了 ——
历史索引不需要你预先定义任何组合，它是从你实际记录过的东西里自动长出来的。

保留此节仅作为决策记录。

### 3.3 LogEntry（一次记录）

| 字段 | 说明 |
|---|---|
| `date` / `time` | 记录归属 |
| `meal` | 早/午/晚/加餐，可由时间自动推断后手动改 |
| `refType` / `refId` | 指向 Food 或 Dish |
| `amount` / `unit` | 份量 |
| `snapshot` | **记录当时的计算依据快照**：名称、基准量描述、四项数值 |

**为什么要 `snapshot`**：如果你三个月后修正了「鸡蛋」的热量值，历史记录不应该被追溯篡改。快照保证历史稳定且可审计。
同时提供**一个显式操作**「按当前食物库重算历史」，让修正是可选的、由你发起的，而不是悄悄发生的。

### 3.4 DayHealth（每日消耗）

`date` · `activeKcal` · `restingKcal` · `importedAt` · `source`（`shortcut` / `manual`）

总消耗 = `activeKcal + restingKcal`。日期为幂等键，同日重复导入覆盖。

### 3.5 DayPlan（当日目标快照）

`date` · `budgetKcal` · `macroTargets` · `model`（见 §5）

目标值**按天快照**。否则你改了目标，历史每一天的完成度都会被重写。

---

### 3.6 记录不依赖食物库（v0.2 修正）

**这一条推翻了本草案最初的一个隐含前提。**

原设计是：想记录任何东西，都得先在食物表里建档，记录时再去查表。
这对固定食谱还行，对真实生活行不通 —— 外食、换着吃、临时买的东西，
你不可能事先建档，事后也不值得为它单独建一条只用一次的档案。

修正后的模型：

| | 原设计 | 修正后 |
|---|---|---|
| 录入来源 | 只有食物库 | **历史记录**（主）→ 食物库（次）→ 手动填写（兜底） |
| 食物库地位 | 记录的前提 | **可选的便利**，只在需要精确克数换算时用 |
| 三大营养素 | 必填 | **只有热量必填**，营养素可留空 |
| 「每份」克重 | 必填 | 可留空，此时只能用「份」记录 |
| 组合 / Dish | §3.2 定义了两层模型 | **取消** —— 用户每天吃的东西都不同，组合用不上 |

#### 实现上的关键：一个字段都不用加

修正之所以代价很小，是因为 §3.3 已经让**每条记录都存完整快照**。
所谓「自由填写」，就是让快照来自用户手打的值，而不是来自食物库。
于是：

- 汇总、编辑、再次调取全部沿用同一条代码路径
- `entryNutrients()` 对两种记录一视同仁
- 判别只需一件事：`refId` 是否为空

#### 历史索引：记过的东西自动成为条目

`core/history.js` 从全部记录里提炼出「记录过的条目」，按最近顺序去重。
去重键：来自食物库的按 `refId`，手填的按名称。

**历史是捷径，不是冻结的副本。** 从历史再记一次时用的是条目的**当前**值 ——
否则你修正过食物数据之后，会以为自己在用新值，其实没有。
只有当食物条目已被删除时，才退回用它当初的快照，并明确标记「食物已删」。

#### 诚实性的连带影响

营养素变成选填之后，当天的营养素合计就可能是不完整的。此时界面必须
**主动说明**：「有 N 条记录没填营养素，所以这三项合计偏低」。

**宁可让数字显得不完整，也不让它假装完整。** 这是 §1 原则 3 的直接推论。

## 4. 计算规则

### 4.1 份量换算

```
per100g  条目：营养 = 库值 × (克数 / 100)
perServing 条目：营养 = 库值 × 份数
```

输入侧必须两种都支持，且能在同一个条目上换算（`1份 = 50g`，所以输入 75g 等价于 1.5 份）。

### 4.2 生重 / 熟重（必须显式处理）

100g 生米约 346 kcal，100g 熟米饭约 130 kcal，差 2.7 倍。这是自填热量表最大的错误来源。

处理方式：`state` 字段为必填；记录时界面常驻显示「生」或「熟」；同一食材允许同时存在生、熟两个条目，靠命名和 state 区分。

### 4.3 汇总

```
单条记录营养 = 库值 × 份量系数
组合营养     = Σ 其 items
日摄入       = Σ 当日所有 LogEntry
净差         = 日摄入 − 当日总消耗
```

## 5. 目标与净差模型 —— 已定：实时预算（修正形态）

### 5.1 决策

采用**实时预算**。营养素目标用**克数**设（蛋白 140g / 脂肪 60g / 碳水 250g），百分比仅作展示。理由：蛋白需求通常按体重算（1.6 g/kg），用百分比设会让它在低热量日被压得过低，反而吃不够。

### 5.2 为什么不能按字面实现

字面形式 `预算 = 今日已消耗 − 赤字` 在上午完全不可用。举实际数：早上 08:00 只消耗了 650 kcal（静息 600 + 活动 50），赤字目标 400 → **今日预算 = 250 kcal**，早饭没得吃。数字要到晚上才涨到正常值。

### 5.3 修正形态

```
今日额度 = 基线预算 + max(0, 今日活动消耗 − 日常活动基线)
```

- **基线预算** = 近 7 天平均**静息**消耗 + 日常活动量 − 赤字目标。
  静息代谢是人体最稳定的指标之一，日间波动极小，因此这个基线既稳定又几乎不含估算成分。它是当天固定的，早上醒来就能看到完整额度。
- **实时加成** = 仅有**超出日常水平**的那部分活动实时计入。下午跑 500 kcal、超日常基线 300 → 额度变为 2350。整天没动则不加成，不会凭空多出额度。

### 5.4 界面约束

**「基线预算」与「运动加成」必须分开显示，不得合并成一个数。**
原因：手表对活动消耗存在系统性高估，且「运动换食物」会诱发补偿性进食。让用户看到 `+300` 是运动赚来的，比给一个模糊的 2350 更诚实，也更符合 §1 的原则。

### 5.5 已知风险

实时预算要求当日消耗数据是新鲜的，而 §7 的数据桥是**手动触发**的（见 §7.5）。若同步频率过低，预算会基于过期数据计算。必须显示**数据新鲜度**（如「消耗数据：35 分钟前」），而不是假装它是实时的。

### 5.6 冷启动

基线预算依赖「近 7 天平均静息消耗」。**首次使用时历史为空**，直接套用会产生一个没有意义的数字。

渐进策略：

| 已有完整天数 | 基线来源 | 界面表现 |
|---|---|---|
| 0 | 不显示预算数字 | 「正在积累数据，暂不显示预算」 |
| 1–2 | 已有天数的均值 | 数字旁标注「数据积累中：第 N/7 天」 |
| 3–6 | 已有天数的均值 | 同上，置信度提示逐步减弱 |
| ≥ 7 | 近 7 天均值 | 正常显示，无提示 |

**不得用体重/身高/年龄套 BMR 公式来填补这段空白。** 那正是「估算」，与 §1 原则 1 直接冲突；而且它会在用户第一次打开应用时就把一个猜测值伪装成测量值。宁可显示「暂不显示」。

## 6. 记录流程与界面骨架

**核心指标：记录一条 ≤ 3 次点击 + 1 次数字输入。** 日频操作的摩擦决定这个应用会不会被弃用。

- **今日页**：**主角数字 = 今日剩余额度**（占满屏幕）。摄入、消耗、基线、运动加成全部作为它的注脚，可展开查看。下方为三大营养素进度、今日记录列表、以及**数据新鲜度与完整度提示**（「消耗数据：35 分钟前」「今天可能漏记了午餐时段」）

  为什么主角是「剩余额度」而不是「今日摄入」：在实时预算模型下额度全天变动，用户真正要做决策的时刻（站在冰箱前、点外卖前）需要的不是「我今天已经吃了多少」，而是「我还能吃多少」。摄入量是过程指标，剩余额度是决策指标。
- **记录流程**：搜索或「最近使用」 → 选食物 → 数字键盘输份量 → 完成
- **食物库页**：列表 / 新增 / 编辑 / 核对标记 / 显示 `verified` 状态
- **组合页**：新建组合 = 加食材 × 份量
- **设置页**：目标、预算模型、导出

**餐次分组：不做。** 记录只带时间戳，不要求用户选早/午/晚。

代价是「数据完整度」提示失去了直接依据（原方案靠「哪一餐没记」判断）。补救方案：应用从用户自身历史中学习惯常进食时段（如 08:00 / 12:30 / 19:00 附近），当某个惯常时段整段空缺时提示漏记。

**用户付出零额外操作，但诚实信号得以保留。** 这是 §1 原则 3 在减少操作摩擦前提下的可行实现。

## 7. 健康数据桥（快捷指令）

### 7.1 为什么必须走剪贴板

两条 WebKit 官方记录排除了更优雅的方案：

1. 从其他应用打开一个落在 PWA `scope` 内的 URL，**只会开成 Safari 标签页**，不会唤起已安装的 Web App（WebKit bug [318623](https://bugs.webkit.org/show_bug.cgi?id=318623)，状态 NEW）。
2. 主屏幕网页应用的存储与 Safari **是隔离的两套**（WebKit bug [181849](https://wiki.webkit.org/show_bug.cgi?id=181849)）。

所以 URL 参数传值这条路，两层原因各自独立地堵死了。

### 7.2 方案

1. 快捷指令「查找健康样本」读取当日的活动能量与静息能量
2. 汇总为一段纯文本，**复制到剪贴板**
3. 时间触发的个人自动化（iOS 15+ 可设为「立即运行」，不弹确认）在固定时间静默执行
4. 你打开应用，点一次「导入今日消耗」

### 7.3 Payload 格式

纯文本而非 JSON —— 便于人工核对，也更抗格式错：

```
CAL/2026-07-14
ACT=842
RST=1710
```

日期为幂等键：同一天重复导入即覆盖，不会重复累加。

### 7.4 已知风险

快捷指令读到的健康数值**未必等于健康 App 里显示的数字**。这个问题有公开报告，必须在首次导入时与健康 App 手工对账，对不上就先解决它再继续。

这是整条技术路线里**唯一可能致命、且完全不需要任何基础设施就能验证**的环节，因此排在 M0 第一位。

### 7.5 两种同步模式（⚠️ 待 M0 实测决定）

§7.1 的两条 WebKit 限制**只在「装到主屏幕」的前提下成立**。如果改为在 Safari 里当书签使用，存储是同一个容器，快捷指令便可直接带参数打开 URL，实现全自动写入。

| | 甲：装到主屏幕（PWA） | 乙：Safari 书签 |
|---|---|---|
| 健康数据同步 | 手动，每次点一下粘贴 | **全自动，零操作** |
| 界面 | 全屏、无浏览器框架，接近原生 | 带 Safari 顶栏底栏 |
| 离线能力 | Service Worker 缓存，较可靠 | 同样可缓存，较弱 |
| 与实时预算（§5）匹配度 | 勉强，需频繁手动粘贴 | **天然契合** |
| 已知隐患 | 存储与 Safari 隔离（bug 181849） | 每次同步可能新开标签页；清 Safari 数据会丢库 |

**倾向**：由于 §5 采用实时预算，需要高频数据流入，方案乙在逻辑上更自洽。但以下事实**必须实测确认，不得靠推测**：

1. 快捷指令「打开 URL」在真机上是否确实进入 Safari 而非其他容器
2. 反复同步是否会累积标签页，以及 Safari 的标签自动关闭策略能否缓解
3. 两条路径下数据在不同会话间的持久性

这三条与 §7.4 的健康值对账，共同构成 M0 的验证清单。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 快捷指令数值 ≠ 健康 App 显示值 | M0 阶段与健康 App 对账，不一致则先排查 |
| 剪贴板被其他应用覆盖 | 日期幂等 + 可随时手动重跑快捷指令 + 手输兜底 |
| 本地存储被清空（清 Safari 数据等） | 一键导出 JSON；建议固定频率导出到「文件」 |
| 主屏幕 Web App 存储被 iOS 回收 | 同上；需在真机上验证实际行为 |
| 应用被误删 | 导出文件可完整恢复食物库与历史 |
| 攒了半年的食物库一次性归零 | **这是本应用最严重的失效模式**，导出功能不是可选项 |

## 11. 开发与测试方式

手机上装的版本走 GitHub Pages，所以每次改动都是「提交 → 等 Pages 构建 → 手机上刷新」，**这个循环慢，不适合调逻辑**。

分工：

- **逻辑开发在主机的浏览器里做**。`core/` 是不依赖浏览器的纯模块，绝大多数功能（食物库、份量换算、营养汇总、预算计算、漏记推断）都能在主机上快速验证。
- **只有真机相关的东西需要上手机**：剪贴板读取、Service Worker、主屏幕安装、健康数据导入。这些恰好就是 M0b 要验的那几项。

**注意**：iOS 上剪贴板 API 需要 HTTPS 安全上下文，所以走局域网 HTTP 调试时它不可用。因此导入功能必须同时提供**手动粘贴到文本框**的降级路径——这既是调试手段，也是真实使用中的兜底（§8 已列为剪贴板被覆盖的对策）。
