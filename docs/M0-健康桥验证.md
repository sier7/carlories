# M0：健康数据桥验证

> 目的：在手写任何应用代码之前，用最短时间证伪或确认这条技术路线。
> 预计耗时：M0a 约 10 分钟；M0b 约 30 分钟（需要先把一个测试页面托管上去）。

---

## 为什么先做这个

整条路线里，只有健康数据这一段可能**根本走不通**。其余部分（食物库、份量计算、营养汇总、预算逻辑）都是确定性工程，写得慢但不会失败。

所以先花 40 分钟验证，而不是写完应用再发现桥搭不通。

**M0a 不需要任何基础设施**，请先做它。

---

## M0a：快捷指令能否读到与健康 App 一致的数值

### 前置：先记下对照值

1. 打开**健康** App → 浏览 → 活动 → **活动能量** → 选择「今天」
2. 记下当前总数，精确到个位：`__________ kcal`
3. 同样查看 **静息能量** → 今天：`__________ kcal`
4. **记下你看这两眼的时刻**：`__________`

数字全天都在涨，所以对照必须**紧接着**做，不能隔几小时。

### 步骤：搭一个最小快捷指令

在「快捷指令」App 新建一个快捷指令，添加以下动作：

| 顺序 | 动作 | 设置 |
|---|---|---|
| 1 | **查找健康样本** | 类型：`活动能量`；筛选：`开始日期` `在今天之后`；`限制` 关闭 |
| 2 | **计算统计** | 操作：`求和`；输入：上一步结果 |
| 3 | **文本** | 把上一步的统计结果拖进来 |
| 4 | **显示结果** | 显示上一步的文本 |

然后对 **静息能量** 重复 1–4（可以复制粘贴那四个动作再改类型）。

运行它，把两个数字记下来：

```
快捷指令 - 活动能量：__________
快捷指令 - 静息能量：__________
```

### 判定

| 情况 | 结论 |
|---|---|
| 两个数与健康 App 一致（差 < 1%） | **通过。** 桥可用，继续 M0b |
| 差正好约 **4.184 倍** | **单位问题**：一个是 kJ、一个是 kcal。修正单位后重测 |
| 差正好约 **2 倍** | 很可能样本被重复计入（如手表与 iPhone 都写了样本）。需要按来源过滤 |
| 数值明显偏小 | 「限制」或被筛选条件截断了，检查是否取到了全天所有样本 |
| 动作不存在 / 报错 | **路线受阻**，需要换方案（见文末） |

### 一定要如实记录

如果数值对不上，**不要将就**。基于对不上的消耗数据算出的「净差」和「实时预算」是假的，而这个应用的全部价值就建立在数字可信上（见设计草案 §1）。

## M0b：实测两种同步模式

在 M0a 通过后再做。需要先把一个测试页面托管到 GitHub Pages。

### 待验证的三个事实

以下是**设计草案 §7.5 中我明确标注为「不得靠推测」**的三点：

1. **快捷指令「打开 URL」在真机上把页面开在哪里** —— Safari？还是已安装的主屏幕 Web App？
2. **反复同步是否累积标签页** —— 如果每小时同步一次，一天会不会攒出 24 个标签
3. **数据在不同会话间的持久性** —— 关掉重开后，页面还能读到之前写入的记录吗

### 测试页面要能回答的问题

- 我是否收到了 URL 参数？（打印 `location.search`）
- 我运行在哪种模式？（`navigator.standalone` / `display-mode: standalone`）
- 我能否读到剪贴板？读到的内容是什么？
- 我刚才写入的记录，重开之后还在吗？（持久化计数器 + 最近一次写入时间）
- 我是哪个容器？（同一页面在 PWA 与 Safari 里显示各自的计数，若两者数字不同即证明存储隔离）

### 两种模式对比

| | 甲：装到主屏幕（PWA） | 乙：Safari 书签 |
|---|---|---|
| 健康数据同步 | 手动，每次点一下粘贴 | **全自动，零操作** |
| 界面 | 全屏、无浏览器框架 | 带 Safari 顶栏底栏 |
| 与实时预算的匹配度 | 勉强 | **天然契合** |
| 主要隐患 | 存储与 Safari 隔离 | 标签页累积；清 Safari 数据会丢库 |

**决策依据**：设计草案 §5 选定的是实时预算，需要高频数据流入。若 M0b 证明模式乙的标签页问题可控，则倾向乙；若标签页会失控，则退回甲并**下调同步频率预期**，同时在界面上显著显示数据新鲜度。

## 如果 M0a 失败

按顺序尝试，不要跳步：

1. **换聚合方式**：改用「统计」动作直接对样本类型求和，而不是先取样本列表再统计
2. **换数据类型**：试 `基础能量`，或试 `总能量消耗`（若设备提供）
3. **按来源过滤**：只取 Apple Watch 写入的样本
4. **换时间窗口**：用显式的「今天 00:00 至现在」而不是「今天」这个相对条件

如果四条都试过仍不一致，则**消耗侧的数据不可信**，此时应当：

- 放弃「净差」与「实时预算」，退回到只记录摄入、消耗仅作参考展示
- 或改为定期手工抄录健康 App 的数字（可靠性最高，但每天花 20 秒）

这个退路不影响应用主体。食物库、份量计算、营养汇总全部照旧，只是 §5 那一章要重做。
