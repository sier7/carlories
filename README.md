# Carlories

个人专用的卡路里与营养记录应用。

不是估算器。日常记录的每一步都是 `份量 × 你自己核对过的值` 这一次乘法。

---

## 现在能做什么

**今日**（默认页）

- **`+ 记录一条`** 从三个来源录入，优先级依次是：
  1. **历史记录** —— 你记过的东西。去重后按最近顺序排列，显示「再记一次会加多少」。
     点进去份量沿用上次，通常两下就完成
  2. **食物库** —— 你为精确换算专门建过档的东西（称重的生米之类）。历史里已出现的不会重复列出
  3. **手动填写** —— 外食、临时吃的。**只需要名称和热量**，营养素可以留空
- 总量自动累加，你不做任何计算。主角数字是当日摄入总热量
- 三大营养素合计；没填营养素的记录会被单独点出来，说明合计偏低
- 可设热量与三大营养素目标，显示「还剩 / 超出」
- 可填当日消耗，即时算出**净差**（赤字 / 盈余）
- 前一天 / 后一天任意翻

**食物库**（可选）

- 手录食物：名称、生/熟、基准量（每 100 g 或每份）、热量、三大营养素、可选的纤维与钠
- 实时试算、一致性告警（热量与营养素按 4/9/4 对不上时提示）
- 可以什么都不建 —— 手填一条记录后点「存进食物库」，食物库就自然长出来了
- 导出 / 导入 JSON

### 健康数据

- 快捷指令定时读取 Apple Watch 的活动能量与静息能量，写进一个 GitHub Gist（你自己的账号）
- 应用每次打开**自动拉取，零点击**。ETag 缓存让重复打开几乎不消耗 GitHub 配额
- 导入按日期幂等：同一天重复同步不会累加
- 落地后即时算出**缺口**（消耗 − 摄入）
- 没配信箱时会退回读剪贴板，那时需要点一下（iOS 系统限制）

**为什么是 Gist**：本来做的是 Cloudflare Worker，但 `*.workers.dev` 在国内被
DNS 污染，手机根本拉不到；Gitee Pages 也已下架。而 GitHub 这条路本来就是通的
—— 应用本身就托管在那上面。用 Gist 而不是仓库文件，是因为它按文件名覆盖、
**不需要处理 sha**，快捷指令少一半动作，也不产生 commit 噪音。

读取公开 Gist **不需要任何凭据**，所以写入用的 token 只存在于快捷指令里，
应用里一个口令都没有。

配置步骤见 **`docs/自动同步.md`**。

### 在手机上

- Service Worker 缓存全部资源，**断网也能打开**
- 有应用图标，从主屏幕打开是全屏、无地址栏
- 部署脚本一条命令推到 GitHub Pages（`node tools/deploy.mjs`）

### 关于「食物库是可选的」

这是刻意的设计。要求「想记任何东西都得先在食物表建档」，对固定食谱还行，
对真实生活行不通：外食、换着吃、临时买的东西，你不可能事先建档，
事后也不值得为它单独建一条。

所以方向是反的：**记过的东西自动成为可再次调取的条目**；
食物库退化成可选的便利，只用在你确实需要精确克数换算的时候。

## 跑起来

```bash
node tools/serve.mjs          # http://127.0.0.1:5173/
node tools/serve.mjs --lan    # 同时监听局域网，便于手机上看界面
```

必须经 HTTP 打开：应用用的是原生 ES 模块，浏览器在 `file://` 下会因 CORS 拒绝加载。
直接双击 `app/index.html` 是打不开的。

## 装到 iPhone 上

```bash
node tools/deploy.mjs         # 推到 GitHub Pages，打印网址
node tools/verify-site.mjs    # 逐个文件比对线上与本地，确认没有漏传
```

> ⚠️ 不要用 PowerShell 的 `Invoke-WebRequest` 测站点：在这台机器上它连 github.io
> 会 TLS 协商失败，会误报「站点没上线」。用 `verify-site.mjs`，它走 Node 的 fetch。

完整步骤（含快捷指令的逐步配置）见 **`docs/装到手机上.md`**。

## 测试

```bash
npm test              # 四个套件一起跑
npm run test:core     # 265 项：换算、营养、校验、快照、日期、汇总、缺口、载荷、信箱配置
npm run test:ui       # 169 项：模块链接、外壳、今日页、多日视图、图表、食物库、表单、同步设置
npm run test:deploy   #  48 项：对着模拟 GitHub 跑完整部署，含完整性检查与 token 解析
npm run test:gist     #  24 项：对着模拟 GitHub 跑信箱创建，含复用与失效重建
```

`test:core` 覆盖的是**算错就会静默出错**的部分。界面错了看得见，算错了看不见。

`test:ui` 用一个最小 DOM 桩把视图当纯函数直接调用，验证「算出来的数字确实
流到了它该去的位置」。它能证明「不崩、数字对」，**不能证明「好看」** ——
视觉效果仍然只能在真实浏览器或真机上看。

## 三条不能违反的规则

**1. 该冻结的冻结，该活的活。**

- `LogEntry` 存**快照**。你三个月后修正了「鸡蛋」的热量值，历史记录不会被追溯改写。
  受影响的记录会被标为「旧数据」，由你决定要不要更新 —— 而不是悄悄改掉。
- 但**历史索引是捷径，不是冻结的副本**。从历史再记一次时，用的是食物条目的
  **当前**值。否则你会以为自己在用修正后的数据，其实没有。

同一条规则：**数据不该在你不知情的时候改变。**

**2. 留空比编造好。**

三大营养素不是必填。外食时你常只知道热量。逼你填，你只会编一个数字进去 ——
而编出来的数字看起来和真的一样，会污染当天的合计。

留空的话，界面会明确告诉你「有 N 条记录没填营养素，所以这三项合计偏低」。
**宁可让数字显得不完整，也不让它假装完整。**

**3. 导出不是可选项。**

食物表是全手工积累的资产，最严重的失效模式是它被清空。
固定频率导出到「文件」或 iCloud。

## 目录结构

```
app/
  index.html            应用外壳（含 Service Worker 注册）
  sw.js                 Service Worker：断网也能打开
  styles.css            移动优先样式（触控目标 ≥ 44 px，深浅色都适配）
  manifest.webmanifest  PWA 清单，用于装到 iPhone 主屏幕
  icons/                应用图标（由 tools/make-icons.mjs 生成）
  core/                 纯逻辑：不碰 DOM、不碰存储、不碰浏览器 API
    food.js             食物实体、校验、份量换算、营养计算
    log.js              记录条目、快照、自由填写、当日汇总、变更检测
    history.js          历史索引：记过的东西成为可再调取的条目
    balance.js          热量缺口、区间汇总、累计走势
    healthSync.js       健康数据载荷解析 + Gist 信箱配置
    date.js             本地日期工具（刻意避开 UTC）
  storage/              IndexedDB 适配层
    db.js               连接与通用读写（一次性建好全部 store，避免将来迁移）
    foodRepo.js         食物 CRUD、导出、导入
    logRepo.js          记录读写、最近记录
    dayRepo.js          当日消耗、快捷指令同步的落点
    settingsRepo.js     目标设置
  ui/                   视图层
    dom.js              极简 DOM 构造器
    widgets.js          浮层、提示条、表单字段
    format.js           数字与文案格式化
    chart.js            图表几何（纯计算，可单测）
    main.js             应用外壳：状态、加载、事件接线
    dayView.js          今日页（纯函数）
    trendView.js        多日视图：摄入/消耗对比、累计缺口走势、逐日明细（纯函数）
    libraryView.js      食物库页（纯函数）
    foodForm.js         食物录入表单
    freeEntryForm.js    手动填写表单（外食）
    foodPicker.js       记录一条：历史 / 食物库 / 手动填写
    sheets.js           编辑记录 / 目标 / 消耗 / 同步设置
tools/
  serve.mjs             零依赖静态服务器
  deploy.mjs            GitHub Pages 部署（走 REST API，无需 git）
  setup-gist.mjs        创建 Gist 信箱
  verify-site.mjs       逐个文件比对线上与本地
  make-icons.mjs        生成 PNG 应用图标（自带最小 PNG 编码器）
  test-core.mjs         核心逻辑测试
  test-ui-smoke.mjs     界面测试（含最小 DOM 桩）
  test-deploy.mjs       部署流程测试（对着模拟 GitHub API）
  test-setup-gist.mjs   信箱创建测试（对着模拟 GitHub API）
docs/
  design-v0.1.md        设计草案
  装到手机上.md          部署 + 装到主屏幕 + 快捷指令（剪贴板路径）
  自动同步.md            Gist 信箱：零点击自动同步
  M0-健康桥验证.md       健康数据桥的查证过程
```

**为什么 `core/` 不碰 DOM 也不碰存储**：它必须能在 Node 里直接跑测试，
也必须能在将来换原生外壳时整块复用。任何浏览器相关的依赖都属于 `ui/` 或 `storage/`。

**为什么视图是纯函数**：`state + handlers → DOM`。这一层最容易长出
「同一个数字在两处各算一遍」的毛病，而那种 bug 不报错，只让总数对不上。

**为什么 `snapshot` 与 `food` 同构**：`entryNutrients()` 因此可以直接复用
`nutritionForAmount()`，不需要第二套计算路径 —— 两套路径迟早会算出不同的数。

## 还没做的

| | 说明 |
|---|---|
| **记录导出** | 目前导出只含食物库，**不含饮食记录和当日消耗**。历史记录现在是主要录入来源，这个缺口比其他任何一项都严重 |
| **健康数据全自动** | 现在靠 Gist 信箱自动拉取，已经零点击；但**取数**仍靠快捷指令定时跑，iOS 的定时触发器没有「每小时」选项 |
| **目标按天快照** | 目前目标是全局的，改了目标过去每一天的完成度会跟着变 |
